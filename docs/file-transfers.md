# Files and background transfers

The file page lists only directories configured by the server administrator. Select a named directory above the list; a directory marked read-only supports browsing and downloads. Host filesystem root paths are configured locally; the phone sends root IDs and relative file names. Writable roots still require an authorized device role for uploads, rename, folder creation, removal and restore.

Select **Upload files** to choose one or several phone documents. Up to 32 local tasks can be retained, including completed history; remove completed records to make room. Individual files may be up to the directory's advertised limit, with an absolute 8 GiB limit. The document provider must report a size and support a persistent read grant. Providers that cannot retain access are rejected with an explanation instead of promising restart-safe transfers.

For downloads, open a file and choose a phone destination. Selecting several ordinary files enables batch download; Android asks for a destination folder and the app creates a separate document for each item. The app does not overwrite an existing phone document through a server path. Android document providers may adjust duplicate destination names.

Transfers run sequentially in a foreground data-sync service with a status notification and **Pause all** action. You can leave the page or background the app. Pause takes effect after an in-flight request reaches its bounded timeout or returns; already accepted bytes are retained. The file page offers individual pause, continue and cancel controls. Changing/removing the active server profile is blocked while the service or file picker is active. Paused tasks are bound to their saved profile ID and canonical server address; they are hidden from other profiles. Each network request uses a captured endpoint and credential and checks the saved pairing again before another chunk.

After process death or app restart, open the file page for the same paired profile and explicitly continue the task. Source/destination URI grants, offsets, root IDs, backend upload IDs and stable request IDs are retained privately. Credentials are decrypted from the saved profile when continuing and are not copied into queue records. Android force-stop, vendor power restrictions and Android's data-sync time budget can stop a service; they do not imply that the file completed.

Upload resume queries the server's accepted offset, including a chunk whose acknowledgement was lost. The phone hashes the entire source stream when continuing; the server verifies the completed SHA-256 before publishing. A finish request keeps its original idempotency ID, so an uncertain result can be checked again without a second publication. A possibly submitted upload publication cannot be cancelled: continue it to verify the original result. A separate, explicitly confirmed local-record discard can clear failed or paused tasks without changing the server result. Profile removal also explicitly clears its local queue and unused grants, even offline or unpaired; pause active work first. Expired server staging requires selecting the source again. Cancelling a paused task removes local state; unavailable server staging remains until its server expiration/cleanup.

Downloads first write an app-private stage using bounded 128 KiB chunks, then copy the completed stage to the chosen phone document. The phone checks space for the remaining stage and keeps 128 MiB free. A changed server identity ticket—including after a backend restart—starts the stage again so prefixes from different file identities cannot be mixed. A stage is removed after successful phone publication or cancellation. A provider failure or cancellation during phone publication can leave an incomplete destination document; the page reports this and the document can be removed manually. Completion is reported only after the phone output stream is flushed.

Select up to 32 ordinary files for batch removal. The confirmation lists a count; the server revalidates each identity ticket and returns per-file results. The result sheet distinguishes moved and unchanged items. Removal goes to this device's recycle area and does not permanently delete files. The server refuses cross-filesystem removal; the original is retained and the error is shown. Restore will not overwrite an existing file.

Older backends without named-root support remain browsable in their original isolated file area. The page shows the original 100 MiB download limit and an explicit upgrade message; background uploads and batch operations require the newer backend. Upgrade the phone app if native background queue controls are unavailable.

## Integration

Include `files-ui.css`. Call `pauseFilePolling()` on page/background changes and `fileConnectionChanged(url,paired,profileId)` when connection/profile identity changes, including profiles with the same URL. The page rejects late replies and stale confirmation clicks.

Native bridge actions are `fileUpload({root,directory})`, `fileDownload({...stat,root})` or `fileDownload({root,items:[stat,...]})`, `transferState`, `transferPause({id})`, `transferResume({id})` and `transferCancel({id})` and `transferDiscard({id})`. Bridge handlers call `files.upload(JSONObject)`, `files.download(JSONObject)`, `files.state()` and `files.command(id,"pause"|"resume"|"cancel")`; preserve `files.result(...)` for SAF request codes 41, 42 and 43 and `files.close()` for Activity teardown. Closing the Activity does not cancel the service. `files.busy()` includes selection, requested startup, active work and queued work.

Manifest integration requires `android.permission.FOREGROUND_SERVICE_DATA_SYNC` and a non-exported `.TransferService` with `android:foregroundServiceType="dataSync"`. It starts only from user-requested enqueue/resume; there is no boot receiver or automatic restart. The service handles Android's data-sync timeout by persisting a pause. Native queue state schema 1 returns `background`, `resumable`, `jobs`, `busy`, `message` and `max_file_bytes`; jobs expose only ID, name, root, kind, bytes, offset, state, message and percent to their active profile, never credentials or content URIs.

New backend requests use root IDs. Read-only recycle listing is **POST `/api/files/trash/list` `{root}`**, distinct from operator-only POST `/api/files/trash` which moves a file. Stable upload request IDs, upload/status and batch-trash are required by the new client contract. `TransferBinding` consumes `ServerSettings.activeId(context)` and `snapshot(context,profileId)` where available, and `StatusClient.request(snapshot,method,path,body)`. Its baseline fallback binds to the active canonical endpoint; it never retargets a queued task silently.

Tests exercise the actual Java engine, private journal, selector/binding, and service against temporary files and Android/transport substitutes. Browser checks exercise real page code with simulated native/API replies. They do not constitute a physical handset, vendor document-provider, or full 8 GiB network transfer test.
